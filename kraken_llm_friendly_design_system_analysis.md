# Монитор ликвидности на Kraken: анализ проекта в связке с самописной LLM-friendly дизайн-системой

**Дата:** 1 ноября 2026 года  
**Принятое пользователем решение:** источник рыночных данных — Kraken вместо MOEX.  
**Назначение документа:** обновлённый архитектурный и продуктовый анализ; не готовая реализация и не подтверждение работоспособности дизайн-системы.

## Основания и границы анализа

Исходные требования взяты из `moex_spread_liquidity_monitor_specification.md` и `HANDOFF-EXTERNAL.md`. Предыдущий `moex_llm_friendly_design_system_analysis.md` используется как контекст ранее выявленных противоречий. Возможности Kraken дополнительно проверены по официальной документации. Все предлагаемые названия компонентов, модели данных, размеры MVP и изменения правил ниже — рекомендации для новой версии проекта, а не уже существующие возможности ДС.

Репозиторий приложения, `tokens.json`, фактический `ds-manifest.json`, схема AST, исходники генераторов и файл Pixso не предоставлены. Поэтому анализ оценивает описанный контракт, но не подтверждает реализацию функций, которые могут существовать за пределами handoff.

## 1. Главный вывод

**Kraken делает проект содержательно сильнее: вместо демонстрации с придуманной глубиной можно построить монитор наблюдаемой ликвидности. Но замена источника не решает ограничения дизайн-системы.**

Публичные потоки Kraken дают котировки и агрегированный стакан L2 без авторизации; официальное описание относит эти рыночные данные к бесплатным. Для предлагаемого приложения не нужны пользовательский торговый аккаунт, приватный API-ключ и операции с деньгами.[^kraken-public][^kraken-free]

В исходном проекте уровни глубины после первого генерировались локально. В новой версии этот генератор следует убрать из рабочего режима, сохранив искусственные данные только в явно обозначенных тестовых сценариях.[^spec-generator]

При этом handoff по-прежнему разрешает лишь существующий каталог, запрещает новые компоненты и не разрешает рисовать графики. Следовательно, полноценный монитор сначала требует согласованного расширения контракта.[^ds-rules]

**Предпочтительная архитектура:**

```text
Kraken Spot WebSocket v2
    ↓
Адаптер: подписки, сообщения, восстановление состояния
    ↓
Нормализованные данные и проверенная локальная книга
    ↓
Детерминированные расчёты и правила событий
    ↓
Модель представления
    ↓
Зарегистрированные аналитические компоненты
    ↓
Экран, собранный LLM по разрешённому контракту
```

Дизайн-система отвечает за представление и допустимую композицию. Адаптер отвечает за протокол. Расчётный модуль отвечает за смысл показателей. Ни один из этих слоёв не следует подменять другим.

## 2. Что сохраняется, а что необходимо изменить

Исходная спецификация предусматривает четыре блока: радар спредов, стакан, ленту инцидентов и баланс с графиком глубины. Эта структура остаётся полезной и после смены рынка.[^spec-layout]

| Область | Исходный документ | Предлагаемая версия Kraken |
|---|---|---|
| Продукт | MOEX Surveillance Desk | «Монитор ликвидности», источник указан отдельно |
| Рынок | Акции MOEX, режим TQBR | Спотовые криптовалютные пары Kraken |
| Стакан | Реальные лучшие цены и синтетическая глубина | Полученная от Kraken агрегированная глубина |
| Объёмы | Лоты и рублёвый оборот | Количество базового актива и стоимость в валюте котировки |
| Временной интервал | Дневной оборот | Оборот за скользящие 24 часа с указанием времени данных |
| Назначение событий | Контроль обязательств маркетмейкера | Превышение настроенного порога и изменения наблюдаемой ликвидности |
| Проверка интерфейса | Зависимость от текущих котировок | Отдельные фиксированные сценарии и проверка реального подключения |
| Источник ошибок | Ограниченность исходных данных | Также корректность поддержки локального потокового стакана |

**Не переносить формулировки «маркетмейкер нарушил обязательства», «предотвращение флеш-крэша» и «давление вниз» как доказанные выводы приложения.** Исходник обещает первые две функции, но новая предложенная модель не содержит обязательств конкретных участников и не доказывает причинные прогнозы.[^spec-business]

Предпочтительная формулировка ценности: «Помогает замечать расширение спреда, понимать структуру доступной глубины и отличать рыночное событие от проблемы данных».

## 3. Предлагаемый объём MVP

Рекомендую один read-only экран, ориентированный на десктоп, без торговли и личного кабинета. Для первой проверки достаточно списка из 12–20 доступных спотовых пар с общей валютой котировки, например USD. Это выбранный проектный объём, а не лимит Kraken.

Конкретный список необходимо проверять по справочнику `instrument`, а не считать вечным. Токенизированные активы и деривативы в этот MVP не включать.[^kraken-instrument]

**Разделение охвата:**

| Возможность | Охват MVP |
|---|---|
| Лучшие цены, спред и положение на радаре | Весь выбранный список пар |
| Детальный стакан | Одна активная пара |
| OBI и кумулятивная глубина | Та же активная пара |
| События превышения порога спреда | Пары с активным наблюдением котировок |
| События изменения глубины | Только период фактического наблюдения L2 соответствующей пары |

Это важное ограничение честности продукта. Подписка на один стакан не позволяет заявлять, что приложение постоянно отслеживает исчезновение глубины у всех инструментов радара. При переключении пары начинается новое наблюдение её L2; прошедшие до подписки события неизвестны.

В первом релизе не нужны несколько бирж, база всей истории рынка, свечной терминал, торговые ордера, приватные каналы, L3, отдельная серверная инфраструктура и работающая в рантайме LLM. Модель нужна для разработки и сборки интерфейса, а не для интерпретации каждого сообщения рынка.

## 4. Какие каналы Kraken использовать

Основное подключение — публичный Spot WebSocket v2:

```text
wss://ws.kraken.com/v2
```

Официальная документация отдельно описывает публичное и авторизованное подключения; предлагаемому приложению достаточно публичного.[^kraken-intro]

| Канал | Роль в проекте |
|---|---|
| `instrument` | Символы пар, базовый актив, валюта котировки, параметры точности и торговый статус |
| `ticker` с `event_trigger: "bbo"` | Лучшие цены для радара и доступные показатели за 24 часа |
| `book` с `depth: 25` | Детализация активной пары: первоначальный снимок и последующие изменения |
| `status` | Состояние торговой системы |
| `heartbeat` | Контроль активности соединения |

Эти роли основаны на спецификациях соответствующих каналов.[^kraken-instrument][^kraken-ticker][^kraken-book][^kraken-status][^kraken-heartbeat]

### Важная настройка радара

У `ticker` по умолчанию выбран триггер `trades`. Для монитора спредов нужен `bbo`: публикация при изменении лучших цен. Само наличие WebSocket не гарантирует подходящую семантику обновлений.[^kraken-ticker]

Пример запроса для двух символов, которые предварительно подтверждены справочником:

```json
{
  "method": "subscribe",
  "params": {
    "channel": "ticker",
    "symbol": ["BTC/USD", "ETH/USD"],
    "event_trigger": "bbo",
    "snapshot": true
  },
  "req_id": 101
}
```

Для активной пары:

```json
{
  "method": "subscribe",
  "params": {
    "channel": "book",
    "symbol": ["BTC/USD"],
    "depth": 25,
    "snapshot": true
  },
  "req_id": 102
}
```

Kraken поддерживает несколько вариантов глубины, включая 25 уровней на сторону; это не означает 25 отдельных заявок или всю книгу рынка.[^kraken-book]

`status` и `heartbeat` не нужно подписывать вручную: их профильные спецификации описывают автоматическую отправку. При этом общий guide по переподключению содержит противоположные примеры. Для реализации следует опираться на схемы конкретных каналов и проверить поведение интеграционным тестом, а не копировать общий пример без сверки.[^kraken-status][^kraken-heartbeat][^kraken-reconnect]

### Роль REST

REST оставить для диагностики, отдельных снимков и при необходимости загрузки вспомогательной информации. Не опрашивать каждый стакан отдельным частым HTTP-запросом. Kraken указывает отдельное ограничение публичного REST по IP; частота не более одного запроса в секунду описана как находящаяся в пределах лимитов. Это не универсальная квота каждого отдельного виджета.[^kraken-limits]

Снимок REST нельзя молча присоединять к WebSocket-изменениям как заведомо согласованную базу. Для потокового режима использовать снимок той же подписки.

## 5. Единая модель данных: сначала смысл, затем виджет

Компоненты не должны получать сырые сообщения Kraken. Предлагаю нормализовать три группы объектов: справочник инструментов, котировки для радара и проверенный стакан активной пары.

В справочнике нужны идентификатор, символ, `base`, `quote`, шаг цены и правила отображения. Внутренний идентификатор можно задавать как `kraken:spot:BTC/USD`, но визуальный компонент не должен разбирать его строку самостоятельно.

Для WebSocket v2 следует использовать символы из `instrument`, а не самостоятельно преобразовывать любые имена REST. Например, документация v2 прямо указывает `BTC`, а не `XBT`.[^kraken-intro]

В современных описаниях `instrument` присутствуют `price_increment`, `price_precision`, `qty_increment`, `qty_precision` и рекомендованная точность отображения цены. Устаревающий `tick_size` не стоит выбирать основой новой модели. Точность ввода ордера, точность исходных данных и точность визуального округления — разные задачи.[^kraken-instrument]

Ниже — **эскиз предлагаемого контракта**, не существующий интерфейс из репозитория:

```typescript
type DecimalText = string;

type OrderBookViewModel = {
  instrumentId: string;
  symbol: string;
  base: string;
  quote: string;
  sourceMode: "live" | "replay" | "fixture";
  integrity: "syncing" | "valid" | "desynced";
  subscribedDepth: number;
  availableBids: number;
  availableAsks: number;
  sourceTimestamp: string | null;
  receivedAt: string;
  revision: number;
  bids: Array<{ price: DecimalText; quantity: DecimalText }>;
  asks: Array<{ price: DecimalText; quantity: DecimalText }>;
};
```

`revision` здесь — локальная версия подготовленного состояния, а не выдуманное поле протокола Kraken. Транспорт, торговый статус и результаты расчётов можно хранить рядом в отдельных типизированных моделях.

**Для выбранного инструмента стакан, его спред, OBI и глубина должны происходить из одной согласованной версии локальной книги.** Не следует брать спред активной панели из одного потока, объёмы из другого и требовать от них идеального совпадения во времени. Радар при этом вправе использовать свои L1-данные.

## 6. Метрики: что пересчитать и как подписывать

### 6.1. Спред

Сохраняем нормирование к средней лучшей цене из исходной спецификации:[^spec-math]

```text
mid = (bestAsk + bestBid) / 2
spreadAbs = bestAsk - bestBid
spreadPercent = spreadAbs / mid × 100
spreadBps = spreadAbs / mid × 10 000
```

Рекомендую основной формат для компактных значений — базисные пункты, с объяснением «1 б.п. = 0,01%». Это уменьшает риск показывать визуальный ноль при округлении небольшого положительного спреда. Проценты можно оставить как дополнительное представление.

Дополнительно полезен показатель `spreadTicks = spreadAbs / priceIncrement`, если известен корректный шаг цены. Сопоставление в процентах и в шагах решает разные задачи, поэтому одно не заменяет другое.

Отрицательный спред не относится к состоянию «норма»: его нужно направлять на проверку данных/состояния рынка. Отсутствие значения не преобразуется в ноль. Сравнение с порогом выполняется до визуального округления.

### 6.2. Пороги и события

В исходнике текстовые границы `0,5% / 1,5%` расходятся с кодом, где при стандартном параметре используются `1% / 2%`. Смена API этого расхождения не исправляет.[^spec-math][^spec-code]

Для Kraken рекомендую отказаться от неподтверждённых универсальных «биржевых норм». Настройки должны называться порогами наблюдения, а не правилами биржи.

Разделить фильтр видимости радара и критерии событий. Изменение фильтра не должно переписывать смысл исторических предупреждений. В событии сохранять инструмент, фактическое значение, применённый порог, версию правила, время, режим данных и область наблюдения.

Для устойчивой ленты предлагаю состояние «открыто → обновлено → завершено», задержку подтверждения и разные условия открытия/закрытия. Это проектное средство против мелькания статусов и дубликатов, а не требование Kraken. Длительности и пороги фиксируются настройками и проверяются на сценариях.

Фраза «спред вырос в четыре раза» допустима только при определённой базе сравнения. Для MVP такую метрику лучше отложить, чем выдавать первое полученное значение за историческую норму.

### 6.3. Оборот за 24 часа

В `ticker` поле `volume` относится к базовому активу, а `vwap` — к средневзвешенной цене за 24 часа.[^kraken-ticker]

Из определения средневзвешенной цены следует расчёт:

```text
turnoverQuote24h ≈ volumeBase24h × vwap24h
```

Знак приближения отражает точность опубликованных исходных полей. Оба значения должны относиться к одному обновлению и одному периоду. Нельзя считать `volume` готовой суммой в USD или подменять оборот произведением объёма на последнюю цену.

Для первого радара использовать одну валюту котировки. Иначе суммы в USD, EUR и BTC становятся несопоставимыми без отдельной конвертации. USD и USDT также не следует молча объединять.

На оси писать «Оборот за 24 ч., USD». Показатель считается актуальным на время использованного тикера, а не на каждую секунду интерфейсного таймера. При BBO-триггере не предполагать гарантированную частоту обновления статистики, когда лучшие цены не меняются.

### 6.4. OBI

Сохраняем формулу из исходника, уточняя границы наблюдения:[^spec-math]

```text
OBI_N = (Σ bidQuantity[1..N] − Σ askQuantity[1..N])
        / (Σ bidQuantity[1..N] + Σ askQuantity[1..N])
```

Для MVP использовать базовое количество в обеих суммах и подписывать «OBI по 25 уровням». Фактическое число доступных уровней показывать отдельно. Если одна сторона короче, не скрывать это под обещанием полного покрытия.

«Объём покупки 60%» не означает «60% покупателей»: здесь нет подсчёта людей. Само значение OBI не является прогнозом направления цены. Нейтральная подпись — «Доля объёма на стороне покупки».

При несинхронизированных данных показатель недоступен. При нулевой сумме знаменатель не определён. Для достоверно односторонней книги рекомендую отдельное состояние вместо обычного индикатора баланса; это сознательное продуктовое правило, а не математическая невозможность граничного OBI.

### 6.5. Глубина

Кумулятивную глубину строить по полученным уровням: для каждой стороны суммировать количества либо стоимость `price × quantity` — с явно выбранными единицами.

25 уровней не соответствуют одинаковому ценовому расстоянию у разных инструментов. Поэтому OBI и глубина здесь описывают локальную структуру выбранной пары, но не дают автоматически сопоставимый рейтинг всего рынка.

Метрику «ликвидность в пределах ±10 б.п.» можно добавить позже. Однако сначала потребуется проверять, покрывает ли полученная книга весь этот диапазон. Если нет, отображается нижняя оценка или «недостаточная глубина», а не уверенный итог.

## 7. Надёжный стакан: обязательная инженерная часть

Официальная схема `book` задаёт снимок и последовательные изменения. Один пакет может содержать несколько изменений одной цены. Руководство по checksum требует удалить уровень при `qty = 0`, ограничивать книгу глубиной подписки и сохранять точность десятичных значений при декодировании. Контрольная сумма охватывает верхние 10 уровней каждой стороны, независимо от выбранной глубины.[^kraken-book][^kraken-checksum]

На этой основе предлагаю следующие инварианты приложения:

| Ситуация | Требуемая реакция |
|---|---|
| Первая подписка | Дождаться снимка; не рассчитывать полноценные метрики из отдельных изменений |
| Несколько изменений одной цены | Применить последовательно, не сортировать сообщения по timestamp |
| Изменение уровня | Установить новое совокупное количество, а не прибавить его к старому |
| Нулевое количество | Удалить уровень |
| Уровень вышел за границу подписки | Удалить из поддерживаемой книги при усечении |
| Несовпадение checksum | Пометить книгу недостоверной, остановить новые рыночные выводы и запросить новую синхронизацию |
| Переподключение | Перестроить книгу из нового снимка, не склеивать сообщения через разрыв |
| Смена пары | Не позволить запоздалому сообщению прежней подписки заменить активную панель |

Рекомендации по повторной подписке и перестроению состояния также содержатся в официальном руководстве по восстановлению соединения.[^kraken-reconnect]

**Необходима точность до парсинга, а не после.** Преобразование уже округлённого JavaScript `number` в строку не возвращает потерянные цифры. Для протокольного слоя нужен декодер, сохраняющий десятичное значение; форматирование для пользователя выполняется позже.[^kraken-intro]

Пропуск массива `asks` в частичном обновлении означает отсутствие изменений этой стороны, а не исчезновение всех продавцов. Состояние стороны определяется по восстановленной книге, не по одному пакету.

При глубине 25 нельзя писать «все 25 уровней подтверждены checksum»: протокольная проверка ограничена первыми десятью. Более глубокие уровни зависят от корректной обработки всего потока; тесты локальной книги должны охватывать их отдельно.

## 8. Состояния интерфейса: больше, чем «API онлайн»

Предлагаю не сводить всё к одному `status`. Независимые признаки могут сочетаться:

| Измерение | Примеры |
|---|---|
| Происхождение | Реальный поток / воспроизведение записи / искусственный сценарий |
| Транспорт | Подключение / соединение открыто / переподключение / отключено |
| Торговая система | Обычный режим / обслуживание / ограниченный торговый режим |
| Целостность книги | Ожидание снимка / согласована / рассинхронизирована |
| Покрытие | Подписано 25; получено 25/25 либо меньше |
| Рыночный критерий | Порог не превышен / предупреждение / критический порог |

Это предлагаемый контракт приложения. Конкретные значения исходного торгового статуса берутся из каналов `status` и `instrument`, а не выводятся из факта открытого сокета.[^kraken-status][^kraken-instrument]

**Нет новых котировок — не обязательно потеря соединения.** `heartbeat` появляется примерно раз в секунду при отсутствии других сообщений; следует проверять активность всего соединения, не только отдельного символа.[^kraken-heartbeat]

Разделить время последнего полученного сообщения, время последнего изменения цены и время последнего подтверждённого состояния книги. Надпись «цена не менялась 30 секунд» не равна «данные потеряны 30 секунд». Вместе с тем heartbeat сам по себе не доказывает здоровье каждой подписки: нужны успешное подтверждение подписки, корректные данные и отсутствие обнаруженных нарушений.

При разрыве можно оставить последние значения, но только с явной маркировкой остановленного обновления. Не переключаться незаметно на искусственный рынок и не закрывать автоматически активные рыночные события как «нормализовавшиеся» из-за потери наблюдения.

## 9. Как должен вести себя экран

Рекомендую сохранить четыре исходные области, но сделать их смысл точнее.[^spec-layout]

**Радар.** Спред в базисных пунктах по вертикали, оборот за 24 часа в одной валюте по горизонтали. При большом диапазоне оборотов рассмотреть логарифмическую шкалу. Нулевые и неизвестные значения не подменять произвольной малой константой ради попадания на график. Выбор точки должен быть доступен не только через точное наведение мыши.

**Стакан.** Лучшие цены находятся у центрального разделителя. Заголовки явно различают цену, количество базового актива и при необходимости стоимость. Масштаб полос одинаков для обеих сторон и объяснён. Уровень идентифицируется стороной и ценой, не индексом массива.

**Лента событий.** Для каждой записи видны причина, инструмент, время, применённое правило и состояние наблюдения. Повторный пакет не создаёт новую карточку того же события. Системная ошибка данных не маскируется под рыночную аномалию.

**Баланс и глубина.** Отображаются единицы, охват уровней и ограничения интерпретации. Больше объёма на одной стороне не превращается в команду покупать или продавать.

Важны устойчивое выделение выбранной пары, предсказуемый порядок элементов и отсутствие постоянных скачков компоновки. При ручном изучении события фокус не должен уходить из-за очередной пересортировки.

Исходное ограничение «без тяжёлых таблиц» не стоит толковать как необходимость строить любые табличные данные из несемантических `div`. Внутренняя реализация согласованного стакана может использовать подходящую разметку. Это не разрешает агенту сборки обходить запрет на неутверждённые компоненты.

## 10. Что потребуется от дизайн-системы

### 10.1. Что уже заявлено

Handoff описывает `tokens.json` как источник токенов, 13 компонентов, закрытый манифест, AST-пайплайн и два эталона — вход и форму юридического лица. React назначен визуальным эталоном.[^ds-state][^ds-rules]

Этого достаточно, чтобы начать проверку архитектуры. Но формы не доказывают готовность к потоковым числовым интерфейсам.

### 10.2. Где контракт не хватает

| Требование монитора | Что видно в handoff | Предлагаемое действие |
|---|---|---|
| Графики | Прямое ограничение | Разрешить конкретные зарегистрированные аналитические компоненты |
| Вложенное содержимое панели | У `Card` перечислены `title` и `description` | Уточнить разрешённые слоты либо утвердить специализированный контейнер |
| Выбор пары и изменение порога | Привязки и действия не раскрыты | Документировать типизированные данные и список действий |
| Статусы риска и качества данных | Есть ограниченный `Badge` | Утвердить отображение состояний без произвольных классов |
| Числа разной точности | Отдельный контракт не показан | Ввести общий форматтер и правила единиц |
| Выдвижная панель, слайдер, тултипы | Отсутствуют в каталоге | Либо согласовать, либо явно пересмотреть требование MVP |

Основание — опубликованный каталог и список отсутствующих компонентов; это не утверждение, что React-код технически лишён этих возможностей.[^ds-catalog][^ds-missing]

Для первого MVP я бы **сознательно отказалась от обязательных `Slider`, `Sheet` и `Tooltip`**. Порог можно редактировать разрешённым полем после уточнения его контракта; детализацию оставить на основном экране; важные объяснения сделать видимым текстом. Это уменьшение объёма продукта, которое нужно записать в новой спецификации, а не тайная подмена компонентов исполнителем.

### 10.3. Что добавить, не раздувая ядро

В прикладном пространстве `market.*` предлагаю зарегистрировать три основных блока:

| Предлагаемый компонент | Ответственность |
|---|---|
| `market.SpreadRadar` | Расположение точек, выбор инструмента, объяснение осей и корректное представление отсутствующих данных |
| `market.OrderBookPanel` | Стакан, числовое форматирование, состояния синхронизации и покрытие |
| `market.LiquidityBalancePanel` | OBI и кумулятивная глубина с единицами и ограничениями |

Ленту событий сначала попробовать собрать утверждённым паттерном из существующих компонентов. Выделять отдельный `market.IncidentFeed`, если повторяемое поведение действительно требует централизованной реализации.

Общий форматтер чисел и конфигурация статусов не обязаны сразу становиться новыми визуальными компонентами. Не нужно создавать универсальный `DataGrid`, конструктор произвольных графиков и десятки вариантов карточек ради одного экрана.

В другой крайности тоже нет пользы: один гигантский `KrakenDashboard` скрывает всю композицию и практически не проверяет, умеет ли LLM собирать интерфейс из системы.

## 11. Токены, семантика и границы ответственности LLM

У существующего handoff перечислены базовые цвета, `destructive`, цвета графиков и числовая шкала. Отдельные роли стороны рынка, качества данных и риска не описаны.[^ds-tokens]

Предлагаю семантически разделить:

```text
market/bid          market/ask
risk/normal         risk/warning         risk/critical
data/live           data/stale           data/invalid
```

Это предложенные роли, не готовые имена в `tokens.json`. Конкретные значения и отображение в Light/Dark утверждаются внутри ДС. Разные роли могут частично использовать одну палитру, но смысл нельзя кодировать только цветом.

Продажа не означает ошибку; покупка не означает безопасное состояние. Критичный спред и красная сторона стакана должны различаться подписью, контекстом и при необходимости дополнительным знаком.

Исходный `DepthLadder` нельзя копировать как образец соблюдения ДС: он использует конкретные цвета Tailwind, произвольный размер `11px`, жёсткие два знака цены и подпись «лот».[^spec-ladder]

В handoff также нужно разрешить неоднозначность `gap: 20`: пример содержит его, но перечисленная шкала `space` не содержит 20. Декоративные интервалы из шкалы, размеры viewport и вычисленные из данных координаты графика должны быть разными категориями ограничений.[^ds-tokens][^ds-assembly]

**Два режима работы с LLM:** разработчик расширения и сборщик экрана.

Разработчик по отдельной задаче может реализовать компонент, адаптер или расчётный модуль, после чего они проходят тестирование и включаются в разрешённый контракт. Сборщик использует только утверждённые возможности. Это не запрет LLM писать программный код вообще; это запрет незаметно расширять собственные полномочия во время сборки экрана.

## 12. AST и React: один источник композиции

Handoff одновременно описывает общий AST и рекомендует прямую React-сборку сложного приложения. Если эти описания экрана редактировать независимо, появится риск расхождения React и Pixso.[^ds-assembly]

Рекомендую тонкий AST: он задаёт структуру экрана, разрешённые свойства, привязки к модели представления и вызовы зарегистрированных действий. Внутренняя логика графика и WebSocket не интерпретируется из AST.

Ниже — **предложение расширения схемы**, не JSON, который уже обязан пройти ваш валидатор:

```json
{
  "id": "spread-radar",
  "component": "market.SpreadRadar",
  "props": {
    "spreadUnit": "bps"
  },
  "bindings": {
    "items": "market.radarItems",
    "selectedId": "ui.selectedInstrumentId"
  },
  "events": {
    "selectInstrument": "ui.selectInstrument"
  }
}
```

Привязки разрешаются через реестр известных типизированных источников; действия — через реестр обработчиков с проверкой аргументов. Не использовать `eval`, произвольный JavaScript, сетевые адреса или формулы, написанные моделью внутри JSON экрана.

Требуются проверки не только существования `component`, но и совместимости данных с этим компонентом, допустимости действия, полноты необходимых слотов и запрета неизвестных свойств. JSX-путь не должен стать обходом тех же ограничений.

Если имеющийся renderer этого не поддерживает, сначала нужен аудит его исходников и ограниченное расширение. По одному handoff нельзя обещать, что подобное подключение уже работает.

## 13. Производительность и расположение адаптера

Для локального прототипа сначала проверить прямое публичное WebSocket-подключение из целевого браузера. В архитектуре без приватных данных сервер не требуется только ради хранения ключа, которого нет. Но сетевую доступность и поведение конкретного хостинга необходимо измерить.

Адаптер держать отдельным от React-компонентов, чтобы при реальной необходимости его можно было перенести в Worker или небольшой серверный посредник. Не вводить этот посредник заранее без причины: у него появятся эксплуатация, собственные сбои и общие лимиты исходящего IP.

**Каждое изменение книги применяется; не каждый пакет вызывает перерисовку.** Можно объединять публикации модели представления, но нельзя отбрасывать изменения до восстановления книги. Анализ событий также должен происходить до объединения кадров, иначе краткое пересечение порога может потеряться.

Как первоначальную настройку для проверки UX можно попробовать обновление радара и числовых панелей раз в 100–250 мс. Это предложение для замеров, не измеренная производительность и не ограничение источника. Если обработка не успевает, нужно уменьшать объём работы или переводить поток в контролируемую ресинхронизацию, а не незаметно пропускать пакеты.

При переподключении использовать нарастающую задержку с разбросом, учитывать обслуживание и отменять ненужные подписки. В прототипе отдельно проверить повторный mount/unmount компонентов, чтобы один экран не создавал несколько независимых сокетов.

## 14. Pixso: что именно считать соответствием

Предлагаемое правило:

> React — эталон работающего компонента. Pixso — зафиксированное состояние его представления на тех же данных, в той же теме и при том же размере экрана.

Для сравнения зафиксировать набор данных, выбранную пару, время сценария, тему, viewport и состояние компонента. Сравнение двух живых экранов, снятых в разные моменты, не является проверкой визуального соответствия.

Сложный график может иметь согласованное статическое представление внутри компонента Pixso. Но возможность использовать растровое превью должна быть явно разрешена: подпись «полностью редактируемый макет» в таком случае неверна. Внешние контейнеры, подписи и управляющие элементы при этом могут оставаться полноценными элементами ДС.

Если все точки, линии и шкалы обязаны быть редактируемыми, это отдельное требование к генератору. Его цену и работоспособность нужно проверять на одном виджете до масштабирования на весь монитор.

Визуальная близость не доказывает правильность данных, а правильный checksum не доказывает доступность интерфейса. Эти проверки независимы.

## 15. Демонстрация и проверка LLM-friendly

Предлагаю три явно различимых режима: реальный поток, воспроизведение записанного потока и искусственный тестовый сценарий. Для начала достаточно живого режима и фиксированных сценариев; полноценный проигрыватель записи можно добавить позже.

Фиксированные данные должны включать весь набор входов, а не только глубину. Иначе текущие котировки снова сделают демонстрацию невоспроизводимой.

| Проверка | Ожидаемый результат |
|---|---|
| Нет нового BBO, но соединение активно | Нет ложной ошибки «сеть потеряна» |
| Нулевое количество на уровне | Уровень удалён; суммарная глубина пересчитана |
| Несколько обновлений одной цены в сообщении | Использован итог последовательного применения |
| Уровень выпал за границу глубины | Книга не разрастается бесконтрольно |
| Несовпадение checksum | Нет новых рыночных выводов из повреждённого состояния |
| Отключение и новый снимок | Старое состояние не смешивается с новым |
| Быстрая смена пары A → B → A | Нет утечки старой подписки в активный экран |
| Неизвестный объём или цена | Отсутствие не превращается в ноль |
| Малая цена или малый спред | Форматирование не уничтожает полезное различие |
| Искусственная аномалия | Явно указан тестовый режим |
| Несогласованный компонент в AST | Сборка отклонена |
| Точечная задача LLM | Изменены только целевые узлы; соседние блоки и токены сохранены |

Все строки этой таблицы — предлагаемые тесты. Они не заявлены как уже выполненные на приложении.

Для проверки LLM дать несколько ограниченных задач: переставить согласованный блок, сменить подпись, добавить разрешённое состояние, подключить утверждённое действие. Измерять прохождение контракта с первой попытки, число ручных исправлений и количество посторонних изменений. Не подменять эти результаты субъективной оценкой «8 из 10».

Проверки `ds:ast`, `ds:audit` и сборки из handoff сохраняются, но дополняются тестами расчётов, потока, привязок и сценариев.[^ds-acceptance]

## 16. Порядок реализации

### Этап A. Проверить две рискованные границы

С одной стороны — короткая проверка публичного WebSocket из реального браузера/хостинга: справочник, BBO, снимок книги, изменения, восстановление. С другой — один зарегистрированный аналитический виджет на фиксированных данных через существующий React/AST/Pixso-пайплайн.

Эти проверки отвечают на разные вопросы. Успешный REST-запрос не подтверждает WebSocket. Успешный React-график не подтверждает генерацию Pixso.

### Этап B. Утвердить небольшое расширение ДС

Согласовать аналитические компоненты, слоты, действия, правила чисел, семантические роли и представление в Pixso. Зафиксировать это в контрактах; не оставлять исключения только в тексте промпта.

### Этап C. Сделать один сквозной сценарий

Выбор пары → подписка на её книгу → согласованное состояние → стакан, спред и OBI → возврат в синхронизацию при ошибке. Использовать те же компоненты с фиксированным набором данных для повторяемой проверки.

### Этап D. Добавить радар и ленту

Расширить L1-наблюдение до выбранного списка пар, не расширяя незаметно обещания по L2. Добавить конфигурируемые пороги и жизненный цикл события.

### Этап E. Проверить изменения, выполняемые LLM

После появления работающих контрактов проверять сборку и точечное редактирование. Только тогда можно оценивать, действительно ли система помогает модели работать предсказуемо.

Не создавать отдельное Vite-приложение автоматически: исходная спецификация и handoff предлагают разные структуры окружения. Сначала определить фактический runtime репозитория ДС и встроить монитор в него.[^spec-stack][^ds-assembly]

## 18. Что фактически проверено в этом анализе

**Проверено по документации:** публичный доступ, каналы v2, триггер BBO, глубина, правила checksum, справочник, состояние соединения и ограничения публичного REST. Использованы официальные источники Kraken, перечисленные ниже.

**Получен ответ API через веб-инструмент:** запрос `Depth` для `XBTUSD` с `count=10` вернул JSON с `error: []` и десятью уровнями на каждой стороне. Это подтверждает получение ответа через данный канал доступа; не доказывает задержку, непрерывность потока или доступность из браузера пользователя.[^kraken-rest-probe]

**Не выполнен живой WebSocket-тест:** попытка из вычислительной среды остановилась на разрешении DNS. Запросы через веб-инструмент с `count=25` и к справочнику также не дали пригодного ответа. Это не доказательство неисправности Kraken или отсутствия соответствующей возможности. Глубина 25 подтверждена документацией, но не практической подпиской в этой проверке.

**Не проверены:** репозиторий, сборка приложения, AST-валидатор, Pixso, производительность, CORS/сетевые политики целевого окружения, длительная работа и восстановление. Описанные выше тесты пока являются критериями будущей приёмки.

Бесплатное техническое подключение также не заменяет проверку применимых условий использования данных при публичном коммерческом запуске. В этом анализе такие права не подтверждались.

## Итог

**Выбор Kraken сохраняет полезную сложность проекта и убирает необходимость имитировать реальный стакан.** Но теперь качество проекта определяется не только внешним видом, а тремя независимыми результатами: корректным состоянием данных, честной интерпретацией метрик и предсказуемой сборкой интерфейса через ДС.

Рекомендуемая формула первого релиза:

> Один источник Kraken Spot. Небольшой список пар с общей валютой котировки. L1 для радара, L2 на 25 уровней для активной пары. Три утверждённых аналитических компонента, контролируемая композиция, проверенные сценарии и явные состояния данных.

Не строить «дизайн-систему Kraken». Строить собственную LLM-friendly систему, которую сложное приложение использует без обхода её правил.
