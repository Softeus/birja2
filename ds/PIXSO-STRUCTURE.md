# Практика хранения компонентов в Pixso

Правила, которые соблюдает пайплайн (`pnpm ds:build`). Руками в файле ничего переставлять не нужно — всё воспроизводимо.

## 1. Страница = уровень ДС

| Страница | Уровень | Что живёт |
|---|---|---|
| `1 Foundations` | 1 | Только переменные/токены. Компонентов нет |
| `2 Atoms` | 2 | Примитивы: действия, ввод, индикаторы, разделители, типографика |
| `3 Layout & Nav` | 3 | Каркас экрана и навигация |
| `4 Molecules` | 4 | Составные блоки общего назначения (контейнеры, оверлеи) |
| `5 Domain` | 5 | Доменные финансовые компоненты |
| `6 Charts` | 6 | Визуализация данных (не рисуем) |
| `7 Gamification` | 7 | Обучение и геймификация |
| `Screens` | — | Макеты экранов, собранные из компонентов |
| `Page 1` | — | Пользовательская страница, пайплайн её не трогает |

Порядок страниц задаётся скриптом: `1 … 7`, затем `Screens`, затем пользовательские.

## 2. Заголовок уровня

На каждой странице уровня — два служебных текста, создаются генератором:

- `_level_title` — «Уровень N · Название»
- `_level_note` — одна строка о назначении уровня

Они не компоненты, пересоздаются при каждом `ds:build`; править их вручную бессмысленно — меняется в `ds/library.spec.json` (`pages[].note`).

## 3. Раскладка компонентов на странице

- Начало сетки — `(0, 0)`; заголовок уровня стоит выше, в отрицательной координате.
- Шаг между наборами — **80 px** по обеим осям.
- Заполнение слева направо, перенос строки при ширине > 1600 px.
- Наборы выровнены по верхнему краю строки.

## 3. Два слоя переменных: Primitive → Semantic

| Коллекция | Режимы | Роль |
|---|---|---|
| `Primitive` | `Default` | Мастер-палитра: `primitive/neutral-0…950`, `primitive/red-600`, `primitive/red-300`, полупрозрачные `neutral-0a10/0a15`. Никогда не привязывается к слоям напрямую |
| `Semantic` | `Light`, `Dark` | `color/*`, `radius/*`, `space/*`, `font/*`. 26 цветовых токенов — **алиасы** на Primitive, остальные (charts, часть sidebar) — сырые значения |

Цепочка: `primitive → semantic → слой/компонент`. Компоненты привязаны только к `Semantic`, поэтому смена ступени палитры меняет все элементы сразу.

- Алиасы ставятся через Plugin API (`createVariableAlias` + `setValueForMode`), потому что MCP-инструмент `write_variables` их не принимает.
- `pnpm ds:verify` проверяет, что каждый алиасный токен действительно ссылается на ожидаемый примитив в обоих режимах.

## 4. Один компонент = один набор
- Все варианты живут внутри своего `COMPONENT_SET` (оси `variant`, `size`, `state`, `checked`, `orientation`, `level`).
- Свободных копий, «черновиков» и переименованных дублей быть не должно: генератор удаляет со страниц уровней всё, чего нет в `ds/library.spec.json`.
- Имя узла = имя компонента в `ds/library.spec.json` и в `ds-manifest.json`.

## 5. Связь с кодом

- Страница задаётся полем `page` у компонента в `ds/library.spec.json`.
- Пропсы, слоты и ключи попадают в `ds-manifest.json` — из него собираются экраны и React-макеты.
- Переименование или перенос компонента — только через спеку, затем `pnpm ds:build`.

## 6. Экранные макеты

- Живут только на `Screens`, каждая рамка — один экран.
- Порядок слева направо задаётся полем `order` в `ds/screens/*.ast.json`.
- Зазор между рамками — 120 px, выравнивание по верхнему краю.
